# 02 技术方案与实现

本地程序管理合成资料、检索、工具执行、消息循环、预算、校验及日志；百炼模型负责问题理解、工具选择、证据冲突判断和最终回答。模型不能直接读取本地文件，必须通过给定工具取得资料。

## 模块与依赖

| 模块 | 职责 |
|---|---|
| `cli.py` | 读取问题、配置模式和保存目录，调用 Agent |
| `agent.py` | P3/P4/P5 路由、观察回传、统一预算、终止和修复 |
| `model_client.py` | Python 标准库 urllib 调用百炼 Chat API，关闭隐藏重试，处理脱敏错误 |
| `mock_client.py` | 有明确标签的脚本化离线模型替身 |
| `retrieval.py` | 资料校验、快照与片段哈希、中文分词、BM25 和融合 |
| `tools.py` | 两个工具的 JSON Schema、参数校验、本地执行及测试故障注入 |
| `schemas.py` | 问题、P3 及最终结果校验，引用与本轮证据匹配 |
| `provenance.py` | 根据本轮实际工具观察检查终止状态与执行轨迹的最低一致性，不读取用例标签 |
| `trace.py` | 写入实际事件及 JSON 结果 |
| `checks.py`、`evaluate.py` | 离线预期核对、套件执行、文档替换和检索/模型对照 |

运行环境为 Python 3.12。中文分词使用 jieba 0.42.1，BM25 使用 rank-bm25 0.2.2，测试使用 pytest 9.2.0，环境配置使用 python-dotenv 1.2.4；完整依赖和传递依赖以 `requirements.txt` 为准。没有使用 Agent 编排框架；HTTP 使用标准库，因此没有 SDK 自动重试消耗未计数的模型调用。

## 模型角色与请求

| 阶段 | single | split |
|---|---|---|
| P3 问题理解、历史消解和 Query 改写 | qwen-plus-2025-12-01 | qwen-flash-2025-07-28 |
| P4 工具选择、冲突查证及最终回答 | qwen-plus-2025-12-01 | qwen-plus-2025-12-01 |
| P5 校验失败后的有限修复 | qwen-plus-2025-12-01 | qwen-plus-2025-12-01 |

P1/P2 的离线数据候选由执行 Agent 按方案整理，未调用百炼生成；P6 只作为可选离线评审模板，当前未运行。P1/P2/P6 仍与原始方案模板一致。P3/P4/P5 已根据首轮真实失败修订，变更与原因见 [真实首轮迭代记录](iterations/real-round1.md)，文件哈希见 [数据与提示词清单](../data/manifest.json)。

请求采用温度 0.1、非思考模式、非流式输出，单次最大输出 2048 token。P3/P5 要求 JSON 对象；P4 提供原生 Function Calling 工具定义并请求每轮一个动作。[configured-03 接通检查](../examples/probe/configured-03/result.json) 已通过：共 3 次模型请求，Plus 工具选择和观察回传验证通过，Flash 的 P3 JSON 校验通过；请求与返回模型分别为指定的 Plus/Flash 固定快照。接通检查只证明账号和协议可用，不代表业务验收通过。

主模型始终收到原问题、相关历史和 P3 辅助结果。P3 不直接回答公司规则或决定是否无资料；程序校验其结构及当前问题中显式数字、产品版次和部分否定/条件词是否保留。该校验是保守的字符串检查，不能证明语义等价；上下文和未覆盖的语义错误仍需检查。

split 的 Flash 请求失败、JSON 不合法或保护字段丢失时，在统一预算内由 Plus 重做 P3 一次并记录回退。P3 仍失败则丢弃改写，以原问题和历史进入 Plus 主循环；不会把错误改写当成事实。主模型服务失败返回 `tool_error`。single/split 的同题双次真实比较已完成。用户随后明确选择“默认全 Plus（推荐）”，交付默认采用 single，split 保留为可选配置。耗时结果仅描述 v3 本次运行，不代表稳定加速或两配置质量相同。

首轮 P3 会把假设的部门、费用类型和制度版本列成缺失信息，主模型有时因此直接追问。修订后的 P3 只列阻碍理解指代或明确请求的必要信息；已明确主题的制度/产品问题交给主模型先检索，不能把缺失信息列表当作必填表单。用户明确认可的修正是：“先检索，有证据就回答”。这不取消适用条件核对或冲突查证。

## 检索与原文

首版保留 8 份短文档，每条完整条款作为一个片段，不做无必要的拆句。在线检索只加载明确指定的文档数组。测试标签、预期动作和用例 ID 不进入知识索引。

索引文本包括标题、正文、范围、版本日期和已有优先级。文本统一 NFKC 和小写处理后经 jieba 分词，过滤常见虚词，保留数字、否定和产品版次。原文保持不变。

原 Query 模式只检索实际执行查询中的第一条 Query；双 Query 模式最多融合两条 Query，每路候选按 BM25 排序，每个名次贡献 `1/(60+rank)`，相同文档/片段去重。实际查询以 `effective_queries` 为准，首次搜索的原问题保护见下文。优先选取不同文档的首个片段，再填充同文档其他片段，减少单一文档挤掉冲突来源的风险。排序不体现制度权威性。

微型语料中的 BM25 分数可能为零或负值，因此是否有词项重叠用于识别候选，不能简单以分数大于零作为命中条件。补检索的查询仍由模型选择。P4 要求首次 `queries[0]` 逐字保留原问题，不同的规范化 Query 放入第二项；第二轮真实记录显示模型并不总遵守该约定，因此 v3 在工具层增加确定性查询保护。

每个请求第一次成功执行搜索时，工具将原问题放在首位，并最多保留一条模型提出的不同 Query；首次参数错误或超时不消耗这项保护。返回的 `requested_queries` 保留模型原始请求，`effective_queries` 记录真正参与搜索的查询，二者可能不同。`original` 模式只执行受保护的原问题，`dual` 模式执行原问题加最多一条改写；此后的搜索按模型选择执行。Trace 同时保留原始参数和真实观察，不能把程序补入的原问题记为模型自主生成。这是检索输入约束，不替模型决定是否检索、读哪份资料或如何回答。

每个请求创建自己的不可变资料快照和索引，计算按 ID 排序、正规化 JSON 后的 `corpus_hash`，片段另有原文哈希。同 ID、日期的正文替换会产生新哈希；新请求重新加载，不复用旧答案缓存。

| 工具 | 参数 | 返回 |
|---|---|---|
| `search_documents` | `queries`：1—2 个非空字符串；`top_k`：1—5；`reason`：一句依据 | 候选 ID、日期、范围、片段位置、短摘录、分数与语料哈希 |
| `read_document` | `doc_id`；`chunk_ids`：1—3 个；`reason`：一句依据 | 完整原文、版本、范围、优先级、片段哈希与语料哈希 |

读取工具使用已有 ID，不接受任意文件路径。搜索摘要只用于定位，正式引用必须来自本轮成功读取的原文。错误统一为 `code/message/retryable`，空结果是成功响应中的空数组。测试故障配置留在工具层，仅接受 `tool/doc_id/times`，生成明确超时观察。

## 动态循环与边界

1. 按配置运行 P3，得到辅助检索信息。
2. Plus 看到原问题、历史、辅助信息和剩余预算，选择工具或最终输出。
3. 程序校验工具参数、登记预算并执行，把实际返回作为对应 `tool_call_id` 的 tool 消息写回。
4. Plus 在下一轮看到完整观察链，再决定补检索、读取、追问、回答或结束。
5. 对最终 JSON 校验结构、来源、引用及最低轨迹一致性；失败时 P5 最多修复一次，不允许修复阶段伪造补检索。

业务流程不读取 `case_id` 决定答案。多工具响应会得到明确协议错误反馈；未知工具、无效参数也成为可观察错误，并计入工具分发预算。两条动态路径必须以实际模型请求和观察链确认，离线 Mock 不计。

默认每个用户请求最多 8 次模型请求、6 次业务工具分发。模型计数包括 P3、失败请求、Flash→Plus 回退、主循环和 P5；工具计数包括失败及参数不合法的尝试。工具额度用尽后仍可基于已有证据生成最终结果；模型继续要求工具或模型额度耗尽则返回 `step_limit`。恰好在额度内完成的合法输出正常返回。

连续相同参数且相同观察会附加未获得新信息提示；同一请求的可恢复错误最多允许一次实际重试。程序不替模型自动重试业务工具。输出校验失败而没有修复预算时，按方案返回 `invalid_output` 并说明原因。

## 历史、冲突与引用

用户历史可以提供产品与版本；历史助手回答不应作为制度事实。普通验收的 C05 将本配置首轮实际回答加入第二轮历史；模型对比则统一使用 single 的首轮实际回答构造双方相同历史，避免输入差异影响对比。二者都不注入预期答案，并要求本轮重新读取当前资料。最终 split 两轮的 Flash P3 仍把上一轮 assistant 的功能结论写入 known_context；后续 Plus 重新读取 D06 并正确回答，但该中间语义缺陷尚未消除。

模型遇到不同规则时须确认对象与条件，读取双方条款，再补查范围、替代关系或裁决依据。日期较新、分数高和更严格都不是独立裁决依据。缺少依据时并列双方引用，给出缺口与追问。D09 仅在单独快照中用于可选裁决验证，不混入基础冲突数据。

最终校验核对字段类型、状态、未完成缺口、追问以及引用 ID/版本/本轮资料哈希。引用须为本轮已成功读取原文的连续子串，`answered` 必须有引用。程序未宣称自动证明语义支持；例如引用包含某个数字，仍可能被错误地用来回答另一个指标，这需要离线断言及人工核对。

首轮真实结果暴露了“未检索却声称未找到”和“读取超时却返回资料不足”的问题。新增 `provenance.py` 只查看实际 `tool_result`：`insufficient_evidence` 需要本轮成功检索；读取失败且没有任何成功读取时，不得用该状态把故障解释为无资料；显式声明 `needs_clarification/document_conflict` 时，至少应读取两份不同文档，并在其后实际分发补检索。`INVALID_ARGUMENTS`、未知工具、动作协议拒绝和预算拒绝都不算实际搜索；已分发但超时的查询只证明尝试，不证明已核实。

正常冲突验收 C02 的离线检查更严格：双方成功读取之后，须有 `ok=true` 且查询涉及适用范围、替代或裁决的补检索。因此参数错误不会再因出现工具名称而被误计为查证。这里仍只检查最低执行事实，不自动推断语义冲突或任意 Query 的充分性；其他原因码的冲突、所有虚构摘要或错误优先级并不能据此完全识别。纯指代不明的追问仍允许不检索。

P4 同时明确：原文支持且没有发现冲突时据原文回答；两方条款中的范围字段为 null 不能证明整个知识库缺少裁决文档；必要读取持续失败用 `tool_error`，不将未核实摘要中的数值复述为业务答案；制度标题不证明权威高于 FAQ，也不支持“主文件”推断。P5 对故障原因的修复仍受真实观察约束。

第二轮中模型虽正确选择 `tool_error`，正文仍复述未读取摘要。因此 v3 在最终呈现阶段增加有限约束：仅当模型已经选择 `tool_error`、本轮没有任何成功读取的原文且确有工具错误时，程序根据实际错误码渲染无法核实的说明，清除未读业务数值和引用。原模型输出仍保留在 `model_response` 及 `safe_error_render` 的 `candidate` 字段，同时记录呈现后的输出。工具动作、重试和结束状态仍由模型选择；程序负责错误信息的可靠呈现，不能把此文本改写宣称为模型自行改正了全部语义问题。

## 记录、评测与技术取舍

Trace 保留模型请求与返回、工具实际参数和观察、前后动作关系、角色和固定模型标识、回退原因、耗时、用量和剩余预算。鉴权头、密钥和内部思考字段不进入记录。每次运行保留资料快照、提示词哈希与源码哈希，旧运行目录不覆盖。

原 Query 与双 Query 对照使用同一资料、问题、Top5 和已标注证据。single/split 对照单独改变 P3 使用的模型，先检查关键缺陷，再比较端到端耗时。没有真实记录时两种收益都保持未验证；P6 自评也不能代替人工验收。

C09 的验收标注已修正过严条件：两份制度期限一致时，一份已读原文即可支持“30 天”答案，`acceptable_evidence_sets` 描述可接受的替代证据组；完整 `required_evidence` 仍保留 D01/D02 以统计已标注证据覆盖。若回答声称两份一致，仍需核实双方。放宽冗余证据要求不等于认可首轮动作依据中错误的“D01 较新/制度主文件”，该问题独立记为 AI 语义审阅发现。旧结果保留，后续称回归验证，不倒改首轮成绩。

v3 稳定后的 [同条件比较](../examples/model_comparison/verified-01/comparison.json) 已完成：single/split 各执行完整 C01—C09 两次，计各 20 次真实请求（含 C05 追问），C10 单独标注 Mock。自动初筛分别为 19/20、20/20；用户在审阅比较后已选择默认全 Plus。具体耗时、失败及完整统计见 [评估文档](03-evaluation.md)。

[split AI 逐条审阅](../examples/model_comparison/verified-01/ai-review-split.json) 核对了全部 20 次真实请求：核心答案、引用、状态和所需工具动作符合用例，但 10 次存在未消除的语义缺陷，包括从 scope=null 推断通用性、从标题虚构主制度地位、把有限检索扩大为全库无资料，以及 Flash 将历史 assistant 结论写入已知事实。持续故障场景的原始提案还可能复述未读摘要或给出未读引用，最终安全输出依赖校验、P5 修复及错误渲染。AI 审阅与自动初筛均不能代替用户验收，也不能支持零缺陷结论。

根据这些实际语义问题，v4 仅修订 P4 的简要依据规则：用通用正反例限制从 null 范围、标题和分数推断权威，禁止把本次空结果扩大为全库不存在，也不因条款一致宣称版本均有效；reason_code 使用可观察动作事实。P1/P2/P3/P5/P6 和合成制度事实没有随该修订改变。新提示词的 [全 Plus 双次回归](../examples/real/final-single-v4/summary.json) 已完成：C01—C09 各两次，共 18 个真实场景执行、20 次真实请求（含 C05 追问），另有 2 次 Mock C10；汇总自动初筛为 20/20 场景执行，不能把其中 Mock 计入真实模型样本。20 次真实请求记录的源码哈希均为 `82feef6eb9fe96f434e4c1e0fee45954b1b451c8de6b11970ad0c266910c7058`。没有对 v4 重做 split 比较，v3 速度差异不作为新版对照结果。

[第一轮语义审阅](../examples/real/final-single-v4/ai-review-repeat1.json) 与第二轮复核未在这 20 次记录中观察到明确的通用范围、主制度或版本均有效推断，这不构成未来不再发生的保证。两轮 C03 仍把空搜索扩大为确认全库无支持资料；第二轮还把一次工具调用中的双 Query 称为“两次检索”，对调用次数的表述不准确，见 [第二轮输出](../examples/real/final-single-v4/repeat-2/C03/output.json) 与 [实际 Trace](../examples/real/final-single-v4/repeat-2/C03/trace.jsonl)。C07 的安全输出仍包含程序错误渲染职责。用户已回复“认可核心结果，保留限制说明”，确认所展示的正常、冲突、工具失败、改20天及冲突移除结果和上述限制；不据此声称人工逐条审核全部20次请求或零语义缺陷。

采用原生有限循环和轻量检索，便于明确分辨模型决策与程序边界。暂不加入微调、强化学习、向量服务或重排组件；如果开发数据表明词面检索有明显漏检，再通过可复现实验决定后续升级。
